> 截至 **2026-11-01**（B1 / B2 / B3 全部落地，12 条策略全部接入内核；缺口只剩真节点验收）。

---

## 一、这个项目是什么

**一句话**：在不改动 BitComet 客户端、也不要求上游软件改配置的前提下，用一个统一入口把下载任务按负载自动分发到多台 BitComet 节点，并把「同一部剧的各集」锁在同一台机器上。

```
上游软件（Aria2 客户端 / 网盘工具 / BitComet 工具）
        │  ① 推送任务（双协议，端口 6800）
        ▼
  ┌─────────────────────────┐
  │   download-gateway       │ ← 管理台（端口 8080，仅内网）
  │   接入层 / 调度层 / 同步层 │
  └─────────────────────────┘
        │  ② 下发（RNCryptor v3 认证 + BitComet WebUI API）
        ▼
   节点1 / 节点2 / 节点3（BitComet 实例）
```

**系统边界**：代理是**调度器 + 状态同步器**，不是下载引擎。真实下载发生在 BitComet 上，代理只能通过其 WebUI API 驱动它 —— 能力上限由 BitComet API 决定。

## 二、要解决的三个痛点

| 角色 | 现在的问题 | 系统给什么 |
|---|---|---|
| 运维者（NAS 管理员） | 3 台 BitComet 各自为战，任务全靠手点，忙的忙死闲的闲死 | 统一入口 + 负载分发 + 一屏总览 |
| 上游软件使用者 | 每台 BitComet 要单独配，节点掉了任务就失败 | 只配一个代理地址；故障自动转移、任务可重试 |
| 连续剧 / 多来源收集者 | 一季几十集散落各机、目录乱、重复下载 | 分组亲和、去重、进度聚合 |

## 五、后续三次范围扩围（重要，别漏）

### 第一次：管理台职责纠偏 + 节点管理（design/08/09）

做四件事：

1. **把「添加任务」从管理台彻底拿掉** —— 任务提交入口**只能**是面向外部的 aria2 / BitComet 原生协议。管理台回归「只看和管」。
2. **从零建起节点管理**：增删改 + 启用/关闭。
3. **设置页从「环境变量清单」改成真正的「派发/负载策略」页**：12 条策略，逐条开关 + 拖动排序（行序即优先级）。
4. **CI 把刚构建的镜像真跑起来做接口冒烟** —— 消灭「镜像从没被运行过」的假绿。

### 第二次：Rust → Go 等价重写（design/10/11/12）

- 起因：团队主栈是 Go，Rust 工具链已卸载。
- 铁律：**对外契约、数据、UI 一个字节都不许变**，只在实现层换语言。
- A 类验收：Rust 侧 160 条可执行用例 **1:1 覆盖**；对外 14 条协议路由 + 管理台全部接口与 UI 不变。
- 明确不做：不改管理台 UI 设计、不引入前端构建步骤、不加功能（**此条后来被第三次扩围覆盖**）。

### 第三次（最重要）：补做调度内核 B1 / B2 / B3（design/11 §2.4 / §3.6、design/13）

**这是整个项目真正的核心缺失**：Rust 版里调度内核**从来没实现过，只有壳**。任务只入库、不下载。
2026-10-08 你拍板：「Go 重构 **+ 补做调度内核**」。

| 阶段 | 范围 | 优先级 |
|---|---|---|
| **B1** | 分组识别 + 阶段0亲和短路 + C1–C5 硬约束 + 软评分 + 建绑 → **投递** → **回读同步** | P0 |
| **B2** | 绑定的**失效与重绑**：strong/weak/manual 分流、rejoin 追平 | P1 |
| **B3** | 跨来源去重（`dedup_index`）+ 命名器（代理前置补名） | P2 |

#### B 类 16 条验收标准（判据只认「结果态」，且必须可证伪）

**B1（7 条）**

| 编号 | 判据 | 错了怎么红 |
|---|---|---|
| B1-AC1 投递真的发生 | `task.node_id` / `node_task_id` 非空且与节点侧对得上 | 没投递 → `node_task_id` 恒空 |
| B1-AC2 回读真的同步 | 一个轮询周期内 permillage / 大小 / 状态被回填为节点读数 | 只建任务不轮询 → 进度停在初始值 |
| B1-AC3 硬约束真生效 | 构造违反约束的节点 → 最终不得成为落点 | 落到本该排除的节点 |
| B1-AC4 同组同节点 | N≥2 个同 `affinity_key` 任务 → `COUNT(DISTINCT node_id) = 1` | 散到多节点 |
| B1-AC5 决策可追溯 | 每次派发/排队/拒绝都在 `dispatch_log` 留痕且自洽 | 无对应行 |
| B1-AC6 失败不静默 | 失败要么退避重试，要么终态且 `error_class ≠ none` | 卡在 queued 且 attempt_no=0 |
| B1-AC7 可安全关闭 | 开关关闭时任务保持 queued、`node_id` 恒 NULL；打开后能落点 | 关不掉或打开不投递 |

**B2（5 条）**：重绑留痕且自洽 / 节点离线不静默 / 容量满不超卖 / 单集失败不牵连其他集 / 24 集同毫秒并发不超卖。
**B3（4 条）**：去重有落账 / 高置信不重复投递 / 中置信不静默（标 `possible_duplicate=1`）/ 命名结构一致。

## 六、九项「做不到」——这是 BitComet API 的上限，不是实现偷懒

| # | 想要 | 现实 |
|---|---|---|
| ① | 提交前知道文件大小 | 拿不到；只能任务建立后回填，之前显示「未知」 |
| ② | 实时推送 / 实时进度 | BitComet **无服务端事件**，只能轮询；进度粒度是千分比 |
| ③ | 目录整洁 | **无列目录 API**，看不到节点磁盘真实目录；只能靠「代理下发即规范」 |
| ④ | 内容级去重 | BT 可用 infohash 精确；HTTP 只能 URL 归一化 + 名称大小启发式，会漏判/误判 |
| ⑤ | 两端口安全 | 代理端口需与节点端口错开；管理口建议只内网 |
| ⑥ | 按磁盘余量调度 | **无磁盘空间查询、无历史统计**（`footer_status`/`statistics_list` 恒空） |
| ⑦ | 下载中跨节点热迁移 | **不支持**；只能在新节点重新创建（重新下载） |
| ⑧ | 强一致进度 | 只能最终一致，且节点「App 访问」关闭期数据陈旧 |
| ⑨ | 登录成败看 HTTP 码 | 登录失败也返 200，**必须解析 `error_code`** |

## 七、明确不做（9 条非目标）

不改 BitComet 本体 · 不扫磁盘文件去重 · 不做下载中热迁移 · 不做实时事件推送 · 不做多租户权限 · 不做媒体库刮削 · 不保证第三方软件全部功能（只保证声明子集）· 不做基于磁盘空间的智能调度 · **不公网暴露管理后台**。

## 十、判断「做完了」的标准

不是「代码写完」，而是：

- **B1-AC1~AC7 全绿，且必须触真节点**（非 mock）；
- B2-AC1~AC5、B3-AC1~AC4 全绿；
- 一次真实操作：从上游软件推到 `:6800` → 管理台看到 → 节点真的在下 → 进度在涨 → 完成。

三项目前**只完成了代码 + 单测/集成层**（B1/B2/B3 共 16 条 AC 全绿，`go test ./internal/...` 22 包全过，
关键断言都做过变异检验），**未在真节点上做一次完整验收** —— 缺节点凭据 + 节点侧「App 访问」开关未确认。

换句话说：**"能不能跑"已经证明过了（假节点 + 真 SQLite + 真 HTTP），"在真 BitComet 上跑起来"还没有。**
生产可用的最后一道门是那一次实机走通，而不是再写代码。
